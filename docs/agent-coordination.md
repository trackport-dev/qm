# Agent coordination

Coordination lets ordinary QM sessions discover peers, spawn independent sessions, and exchange organization-readable messages. It is experimental and remains under qualification. Do not enable it in production until the release gates below are closed.

## Agent workflow

Discover the interfaces through the capability-authenticated `/v1/apis` catalog. Session attribution comes from the current live capability, not a caller-supplied sender or parent ID.

Coordination mutations require a capability bound to the actual session, current run attempt, and original unexpired run lease token. A token from a replaced attempt does not regain mutation access when the same run ID is retried. The reaper's replacement cleanup lease does not authorize the retiring agent. Older tokens without these claims retain their existing non-coordination behavior but cannot perform session-owned coordination operations.

Board publication, spawn reservation, character replacement, wait registration, subtree-limit changes, and execution-limit changes check the run at the storage transaction boundary. PostgreSQL holds the run row lock through commit and checks expiry before committing; mixed PostgreSQL coordination with memory runs holds the memory mutation lock through commit. Pure memory transactions recheck immediately before synchronous writes. This serializes lease replacement with these mutations; it does not guarantee wall-clock lease validity at commit acknowledgment or fence external provider and sandbox submissions. HTTP regressions expire the lease after request authorization and verify that all six paths reject without changing records or limits.

Shared harness tools also recheck the current run lease before entering their bodies. Tool admission closes when the harness returns or fails, before result persistence, and rechecks closure after an asynchronous lease lookup. This prevents late callbacks from starting fresh tool work; it does not cancel already-dispatched sandbox requests or establish an executor-side submission fence.

1. Read `/v1/peers/self` and `/v1/peers` to discover identity and peers.
2. Replace the session's character through `PUT /v1/peers/:id/character`, supplying its current version. Character controls discovery, not authority or ancestry.
3. Reserve a child with `POST /v1/peer-spawns` and `{task, name, character, idempotencyKey}`. Inspect its state and capacity through `/v1/peers/:id/subtree`. Reuse the idempotency key when retrying the same operation.
4. Publish through `POST /v1/peer-messages` with `{text, audience, idempotencyKey}`. Add `replyTo` for a direct reply.
5. To wait, register `{messageId, idempotencyKey, timeoutMs, mode}` through `POST /v1/peer-waits`, then call the shared `wait_for_peer` tool with `{wait_id: wait.id}`. Registration alone does not suspend execution.

Lower execution budgets through `PUT /v1/peers/:id/execution-limits` with both `{concurrencyLimit, turnLimit}`. The current live session is the only allowed target. Concurrency applies to its whole scope; the autonomous turn budget applies to its immutable root tree, including siblings. Updates are durable and serialized with admission, cannot raise either effective limit, and cannot go below active scope executions or already-admitted autonomous turns. Read the effective limits through the subtree inspector before changing them. Deployment configuration remains an upper ceiling.

An audience such as `.[] | select(.group == "new-feature" and .role == "worker")` selects unchanged candidate objects. Use `._qm.id` for individual addressing. Publication freezes the selected recipients and their character evidence. Later character changes do not retarget the message. `empty` publishes without notifying anyone.

Messages remain readable by peers outside their intended audience. Reading, searching, and previewing an audience do not wake agents. A message is not a human instruction or an authorization grant. Private session activity remains subject to its existing access rules.

Initial peer turns and peer steering are labeled `peer-message` in screening payloads, independently of the web or Slack delivery surface. This is provenance, not a screening exemption: authored content still reaches the classifier and strict verdicts still block execution. Existing approval decisions are not cleared or reinterpreted by a provenance-label change.

Wait mode `first` accepts the first qualifying direct reply; `all` requires one from each frozen recipient. Other peers may reply publicly without satisfying the subscription. A wait with no recipients is immediately ready. Deadlines survive registration retries, and replies after the deadline do not satisfy the wait. Suspension releases the worker and session lease; a durable continuation resumes the session after source execution has released. New human input or peer work does not erase the subscription.

## Debugging

Run `npm run demo:board` from `plugins/web-ui` for a local fixture-backed board at `http://127.0.0.1:5189/board/request`. Message permalinks reload into the demo. The fixture shows replies, blocked delivery, zero recipients, waits, and retained spawn ancestry without credentials or running agents. Its lifecycle mutations and arbitrary jq/filter evaluation are not implemented; use the development instance for those checks. This local demo is not a hosted review artifact.

The web UI's Agent board exposes the public timeline, frozen audiences, delivery records, reply waits, and spawn tree. A current audience preview is a new evaluation, not historical evidence. Session links only appear where the viewer has access.

Distinguish these states:

- Published: the message and selected recipient records exist.
- Delivered: a notification was queued or steered; this does not prove model consumption.
- Consumed: the recipient accepted the attributed input; this does not prove a reply.
- Wait ready or timed out: the reply subscription has an outcome; source execution may still need to release before dispatch.
- Wait resumed: its continuation was consumed. Check the linked session for the result of that run.
- Blocked: inspect the safe reason, such as inactive recipient, revoked authority, or pending human approval. Do not clear approvals to force a coordination test through.

Human lifecycle controls distinguish an individual agent from its subtree. Stop and archive preserve history and do not free descendant slots. Existing authorized permanent deletion retains ancestry tombstones for surviving descendants.

Deleted session IDs cannot be reused by spawn retries. Binding checks parent and child existence in the same transaction as the binding, serialized with PostgreSQL session deletion. Deleting a partially provisioned child does not release its unfinished reservation: it remains counted against every ancestor and visible in the tree until resource cleanup can be established. Completed, permanently deleted child sessions may stop counting while their ancestry remains available.

Human character edits require scope-management permission, just like lifecycle controls. Transcript visibility alone does not authorize renaming an agent or changing its character. Agent capabilities may edit only their own live session.

Managed-project capabilities retain the roster version under which they were issued. HTTP regression coverage verifies that removing an execution owner rejects coordination mutations even while its run remains running, and re-adding that owner does not revive the old capability. A fresh authorized run succeeds after rejoining. Deleting the empty session and recreating its conversation with a new session ID also leaves the old capability unable to read self or edit the replacement character. This does not establish the separate channel-roster cases.

Runs bind immutably to the actual session ID before peer identity hydration. The binding requires the current unexpired run lease; a conflicting binding fails closed. Historical authority uses only exact session-ID evidence, including completed legacy results, never the conversation reference alone. An unbound retry without legacy incarnation evidence cannot acquire a new binding. Memory and PostgreSQL regressions cover recreation, first live claims, conflicting rebinding, ambiguous legacy retries, and completed-run backfill; independent review found no remaining issue in this scoped fix.

Execution admission also rejects a missing or replaced thread session when the run already has an exact session binding, including the legacy result fallback. This happens before recording execution start or applying the replacement session's limits. A worker regression verifies terminal rejection without entering the orchestrator. Independent review found no required fix in this guard; it is an admission-time check, not atomic protection against deletion later in the turn.

Worker drain and lease reaping release session locks by the run's recorded session ID and original run lease token, never by looking up the thread's current incarnation. Session lease acquisition atomically records that run ownership in memory or PostgreSQL. Owner-matched cleanup leaves replacement attempts and unrelated compaction leases intact; unbound runs and older unowned leases are not force-released by run cleanup. Both normal and flagged-input processing bind the run's session before acquiring an owned lease. The additive session-lease migration preserves existing records. Explicit administrative forced release remains available separately and is not used by run cleanup.

Memory reaping runs its cleanup callback outside the run mutation lock, while token replacement and final retirement remain serialized; callbacks can inspect or reject stale heartbeats without deadlocking. Regression coverage includes replacement-session locks, owner-matched memory/Postgres cleanup, and memory/Postgres/mixed-store run fencing. Independent review's flagged-input binding finding was fixed and verified at the acquisition boundary. These changes protect session-lock cleanup; they do not establish provider termination or whole-worker execution recovery.

Gated reaper and worker-drain regressions delay cleanup until the same session has a replacement lease. The drain case also releases and reclaims the actual run with a new attempt token before allowing the old cleanup through, verifying that both replacement leases survive. These orchestration tests use memory stores; separate PostgreSQL tests verify owner-matched lease deletion and run fencing.

All serving cleanup workers must use owner-matched release before relying on this protection. An older binary can still issue an unconditional release. Existing unowned leases retain their ordinary expiry and token-based release behavior; the new run cleanup does not infer ownership from a thread name or a lease's age.

Execution permits are fenced by run lease tokens. A persisted termination receipt lets another worker finish an interrupted permit release. A stale receipt cannot release a replacement attempt. An orphan without termination evidence remains charged; lease expiry is not proof that its model or tools stopped. Do not manually clear its database row to recover capacity.

The execution sweeper marks a missing or expired lease as orphaned even before the run reaper retires its token. This is a conservative uncertainty marker, not a declaration that the worker died. A late heartbeat may renew the same run lease, but does not clear the marker or free capacity; the owning execution can still finish and release normally.

Admission checks require an unexpired lease both before and after recording execution start. Expiry before admission leaves an existing permit charged; expiry during the unstarted admission path releases only that unstarted attempt. Regression tests exercise both boundaries. Whole-worker crash recovery remains incomplete: provider termination and pending tool operations are currently tracked by in-process promises, while the background-process registry does not identify every provider execution or foreground sandbox operation. Neither a missing heartbeat nor an empty live-process listing establishes termination.

Background jobs retain their originating run ID and attempt in the process registry; reattachment from another attempt does not rewrite that attribution. Legacy records without an attempt remain unattributed rather than inheriting the current retry. Helper-backed sandboxes register the allocated process ID as `starting` before dispatch and promote it only after launch acknowledgement. Failed or ambiguous launches retain that state. Matching starts, polling, writes, stops, and watches report an unconfirmed launch rather than treating absence as termination. Reconciliation and TTL reaping leave these records intact; live inventory includes them even after TTL expiry so their sandbox cannot be retired as idle. Attempt attribution does not provide a recovery acknowledgement or executor-side submission fence. Adapters without registered-start support cannot launch new background jobs; existing jobs remain eligible for reattachment.

Foreground process-group cancellation now writes a per-operation cancellation marker before looking for the process group. A delayed launch checks that marker after recording its group and refuses to execute, even after the cancellation request's polling window has ended. The marker remains in the sandbox's temporary filesystem; it is not a durable run-attempt registry, a security boundary against filesystem mutation, or proof of termination. Linux runtime tests cover delayed launches, cancellation of a running group, failed group registration, and normal output/exit-code preservation. Whole-worker recovery still needs durable operation identities and trustworthy provider termination evidence.

Recovery requires a durable attempt execution group and an executor-side submission fence. Register operations before dispatch with stable IDs; closing a group must also reject delayed submissions. A separate supervisor must attest to provider-runtime termination, and the sandbox executor must attest that the closed attempt has no outstanding operations. Only those combined receipts can authorize capacity release. The existing process-session exit sentinel is not such an attestation: sending KILL can write it before the process tree has stopped. The local sandbox's executor boundary is `aws/microvm-agent/agent.mjs`; adding a group contract there must preserve files and unrelated processes, and cannot by itself prove that a host-side provider runtime stopped.

A local executor diagnostic submitted a bounded `sleep 2` command, observed the daemon's child process, disconnected the HTTP client, and confirmed that process remained alive afterward. The command exited naturally and the test daemon was stopped. This directly rules out treating client disconnect as executor termination; it does not test worker-process death or establish a recovery protocol. The executor currently has no operation identity, closed-attempt registry, or termination-status endpoint. Recovery implementation must reach this executor boundary and its packaged CLI copy, not just add another core-side receipt.

OpenCode retires a sidecar after ambiguous transport failures or asynchronous steering. Existing turns drain before shutdown; new turns wait for a fresh runtime and can be cancelled while waiting. The affected execution stays tracked until the captured process exits. Already-running sandbox tools remain separately tracked.

## Qualification

PostgreSQL crash tests now run `processRun` in a separate Node process and terminate that exact child with SIGKILL at two controlled boundaries. Each case uses an isolated database schema. A barrier in permit deletion exercises the production release ordering: after a persisted release receipt, a reconstructed execution service releases the still-active permit idempotently. During execution without a receipt, run reaping and repeated execution sweeps retain one orphaned permit and reject a replacement token. The fixture orchestrator performs no provider or sandbox work; these tests establish durable receipt recovery and conservative admission after an actual worker-process death, not termination of external operations or whole-worker recovery. The crash, execution-store, execution-runtime, and worker-admission tests passed together (31 tests), with PostgreSQL enabled and no skips.
